# 2026-09-10 软件清单云端化与实时刷新

## 起因与口径

- 用户方向：软件清单放 env 云端可实时更新，新增软件只需配置播种，不必动 ome（换二进制或发版）。
- 现状盘点：镜像早就有 `ome/catalog/tools.toml` 加 `.sha256` 边车（seed-mirror 路线 B 随 catalog 变更与每日自动推，D31/D32 两次入镜实证）；catalog 解析四级加全 miss 自举；缺口只在消费侧，装完那次之后不再回头读云端。
- 三项定稿（用户令「开工」按建议）：权威落位取「仓库副本是开发与离线兜底源，云端是运行态权威」；刷新时机取「TTL 24h 自动加显式 `ome catalog status/sync`」；信任锚取「镜像自算 sha256 边车，先边车后资产，签名留后」。

## 实现

- 结构（用户第 3 轮裁「catalogsync 与 catalog 应是一个主功能下面的 2 个子功能」）：主功能只留 `catalog` 一个入口与一个模块，`status`（看）与 `sync`（刷）是它的两子功能；原先独立的 `catalogsync` 概念与模块取消，代码并入 `src/catalog.rs`（sync 侧 `sync_to` 加 `auto_refresh*`，status 侧 `catalog_state`）。
- sync 子功能：边车取锚（`?t=` 击穿）→ 资产下载（`?v=<锚>` 击穿）→ sha 校验 → `Catalog::load` 解析验证防半截 → 同目录临时文件替换落位；TTL 走 `.last-sync` 标记（记时刻与锚，不碰 catalog 文件 mtime），本地被改写（self-deploy 或人为）即视为需检查。
- status 子功能：报解析面路径与来源（repo / userdata / env / other）、本地与云端锚、检查年龄、TTL、离线态与云端错误；`ome catalog` 缺省即 status，`ome catalog sync` 显式刷新，不受 `OME_CATALOG_TTL` 与 `OME_OFFLINE` 限制。
- 自动接线：main 在解析 catalog 后、加载前，仅当解析面**就是**用户数据副本时按 TTL 刷新；自动路径先做单次 5s 短超时探活（不重试、不走 curl 兜底），失败写退避标记（TTL 内不再重试），保证网络异常不拖慢用户命令。
- 下载层顺加 `fetch_text_short`（短超时单次取文本）并把 `parse_sidecar_sha` 提为 pub 复用；没有为自动路径引入任何新依赖。

## 验收

- 单测五枚（TTL 解析、标记读写对称与坏内容不采纳、联网四判据、来源分类、动作词稳定）；gated 真网测新增 `tests/catalog_refresh.rs`（`OME_TEST_MIRROR=1`）：首次 updated 且落位件 sha 等于独立取自镜像的边车锚、`Catalog::load` 通过且含 typst、二次 current 幂等、TTL 内 fresh 不联网。
- `cargo test` 全绿（lib 95 加 cli 28 加 catalog_lint 2 加 catalog_refresh 1 加 golden 2 加 install 2 加 mirror 7 加 real 7）；clippy 干净。
- 真机端到端（关键实证）：`ome catalog sync` 把本机部署副本从 E2A0245A 刷到云端 CFF2B44A（含 typst 段）；再用**未含 D33 的旧部署二进制 ome 0.2.1** 在非仓库目录跑 `status`，typst 行三态齐（locked=installed=0.15.1、path=true），即「云端播种加本机刷新，不必换二进制」。
- 关闭与自愈实证：`OME_CATALOG_TTL=0` 时不触发刷新（无刷新提示）；人为在部署副本追加一行制造漂移后，下一次命令自动探测并按锚还原到云端版本，输出 `[OK] catalog 已刷新: …（云端 CFF2B44A）` 且标记落位。

## D34 落地：云端清单签名与内外一起校验

- 用户令「开工」，取建议默认：新建 Ed25519（minisign）签名密钥对；校验强度取「有签名但验不过即阻断，缺签名件只告警」。
- 密钥与工具：`.tools/catalog-sign` 子工程（minisign 库，keygen 与 pubkey 与 sign 与 verify）；本机私钥落 `~/.config/ome/catalog-signing.key`（不进仓库、不进 EnvRoot），公钥 `.tools/catalog-sign/catalog-signing.pub` 进仓库，公钥 base64 内嵌 `src/catalog.rs`，单测机检两处一致（换钥必然红灯提醒同步）。CI 侧 GitHub Secret `CATALOG_SIGNING_KEY` 已配置。
- 客户端：拉取落位前过 sha、解析、验签三重（任一不过拒收，含自举与自动刷新）；签名件随刷新落位 `<清单>.minisig`；每次命令加载运行态副本前巡检，验不过阻断并提示 `ome catalog sync`，缺签名件只告警（本地 pin 回写会主动撤签名，避免留假凭证），catalog 子命令豁免以便自愈；`catalog status` 增 `signature` 与 `pubkey` 字段。
- 流水：seed-mirror 加签名步（缺密钥即失败，不发布未签名清单），`seed.py` 把 `.minisig` 随清单与边车入镜；`ome catalog sync` 自此「验签通过才落位」。
- 关键设计说明（回答「其他机器怎么装私钥」）：其他机器不需要私钥也不需要任何安装步骤，公钥随 ome 二进制分发（`ome init` 与 `self update` 自动到位）；私钥只在开发机与 CI 密钥库出现。轮换走双公钥过渡（先发版内嵌新旧两把，再换私钥重签云端件，机器更新完摘旧钥）；私钥泄露即换钥发版加重签云端件。
- 推送与验收（用户令「推」）：三笔推 main（cb40d72..ff8e81f）；catalog 内容未变，seed-mirror 的 push 路径过滤不触发，改用 workflow_dispatch 手工触发（run 34476432766，签名步绿、1m23s 完成），镜像 `ome/catalog/tools.toml.minisig` 随即 200。
- 端到端实证：本机 `ome catalog sync` 拉取时验签通过并落位签名件（部署副本 `%LOCALAPPDATA%\ohmyenv\catalog\tools.toml.minisig` 在位）；非仓库目录 `ome catalog` 报 origin=userdata 与 synced=true 与 signature=valid 与 pubkey=FB93BFD3788C2316，普通命令零告警。
- 篡改实证分两路：联网状态下改动部署副本，命令前的自动刷新会先用云端件修复（比阻断更友好）；`OME_OFFLINE=1` 时自动刷新停手，签名巡检接管并阻断（exit 1，提示用 `ome catalog sync` 修复），随后 sync 自愈回 valid。gated 真网测（签名件落位与内容篡改拒收）通过。

## D34 评审对线：claude 侧独立复核

- 复核方独立走过 fetch_with_anchor 三重门、main 加载前巡检、sync_to 的 InSync 补签名与 needs_check 四态、CI 缺密钥即失败，并抽测 lib 签名两例与 catalog_refresh 一例全绿；提三点待确认，逐条回复如下。
- 点一（落位临时名硬编码 `tools.toml.tmp`）：确认是真隐患而非仅脆。清单与签名件共用同一临时名，并发刷新时存在「把清单内容 rename 成签名件」的串写窗口。已改 `tmp_path` 随目标名派生（`tools.toml.tmp` 与 `tools.toml.minisig.tmp`），并加单测锁住两条临时名不同与落位后不留残件。
- 点二（rename 失败回退 copy 非原子）：确认可不改。临时件与目标同目录，rename 失败只剩「目标被占用」一途；半截文件的后果是解析失败或验签失败，都会阻断并可由 `catalog sync` 自愈，属响亮失败而非静默错误。已在代码注释写明该取舍。
- 点三（invalid 阻断含 self update）：确认属有意设计。被篡改的运行态清单意味着本机可控面已失守，此时允许自我升级不是修复动作；修复通道只留 `ome catalog sync` 与显式 `OME_CATALOG` 两条有意为之的路径。
- 自评另发现两处未收口并当场修：一，自举路径原先「官方 raw 优先」不过验签（TLS 信任），与 D34 目标不一致，已改镜像优先并强校验，官方 raw 只在镜像不可达时兜底且打 WARN 标注未验签（真机清空部署目录复验：自举落位清单加签名件加标记，status 报 signature=valid）；二，init 与 self update 同步 catalog 时原会无条件撤签名件，导致内容没变也凭空变无签名，已改为只在签名与内容不符时撤。seed-mirror 触发路径同时补上签名工具与流水自身，免得改签名逻辑却不重发。
